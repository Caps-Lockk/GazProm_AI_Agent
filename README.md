# «Сигнал» — ИИ-агент ретрансляции обращений поддержки в разработку

Прототип решения кейса Intelligence Cup («Газпром нефть»). Раз в неделю агент находит повторяющиеся некритичные обращения пользователей и передаёт их продуктовым командам. Каждое предложение он оформляет как черновик задачи с доказательствами. Менеджерам поддержки ничего заполнять не нужно.

```bash
pip install -r requirements.txt
python -m signal_agent demo        # конвейер + агент на 66 синтетических обращениях «Вебнефти»
python -m signal_agent eval        # то же + офлайн-оценка на золотой разметке
python -m unittest discover -s tests -t .   # 28 тестов
python -m finance.model            # финансовая модель: сценарии и потолок инвестиций
```

**Визуальный прогон:** откройте `demo/replay.html` в браузере. Страница пошагово проигрывает настоящий журнал прогона: маскирование ПДн на примерах, вызовы инструментов агента, решение по каждому кластеру, итоговые задачи и дайджест. Пересобрать её после изменений: `python demo/export_run.py && python demo/build_replay.py`.

Для демо не нужны ни сеть, ни GPU. Вместо Qwen 3.8 работает офлайн-модель `MockChat` (см. «Оценка качества»). С внутренними моделями запуск выглядит так: `python -m signal_agent demo --online`, адреса берутся из `config/settings.yaml` или переменных `SIGNAL_LLM_BASE_URL`, `SIGNAL_ASR_BASE_URL`, `SIGNAL_VL_BASE_URL`.

Сбой сайта (ошибка 502) классифицируется как инцидент и до агента не доходит: им занимается дежурная смена. Дайджест владельцу продукта записывается в `out/digests/`, журнал всех вызовов инструментов — в `out/runs/<run_id>.jsonl`.

## Архитектура → код

| Сервис из решения | Модуль | Что делает |
|---|---|---|
| 1 Ingestion | `pipeline/ingestion.py` | Инкрементальная выгрузка по водяному знаку; `JsonlTicketSource` (архив, тесты), `SqlTicketSource` (read-only реплика) |
| 2 Медиа | `pipeline/media.py`, `llm.py` | Звонки → Qwen-ASR, картинки → Qwen-VL; `StubMedia` для офлайна |
| 3 Маска ПДн | `pipeline/pii.py` | ФИО, телефоны, e-mail, ИНН/ОГРН, госномера, логины — **до** любого вызова LLM |
| 4 Извлечение | `pipeline/extraction.py`, `prompts/extract_card.md` | Тикет → JSON-карточка, проверка схемы, 1 повтор, иначе `needs_review` |
| 5 Кластеры | `pipeline/clustering.py` | TF-IDF (символьные n-граммы) + агломеративная кластеризация; интерфейс `Embedder` для эмбеддингов |
| 6 Агент | `agent/orchestrator.py`, `agent/tools.py`, `prompts/agent_system.md` | Цикл tool-calling, 9 инструментов, защиты внутри инструментов |
| 7 Доставка | `delivery/tracker.py`, `delivery/digest.py` | Черновики задач (`SqliteTracker`, набросок `JiraTracker`), недельный дайджест |
| 8 Обратная связь | `storage.py` (feedback, decisions), `metrics.py` | Оценки команд, журнал решений, метрики |

Ночной и недельный контуры разделены и в коде: `python -m signal_agent nightly` (ежедневно в 01:00) и `python -m signal_agent weekly --product webneft` (раз в неделю). Расписанием управляет планировщик (cron или Airflow, см. `docker-compose.yml`). Всё, что относится к конкретному продукту — описание, модули, пороги, канал доставки, — лежит в `config/products/<id>.yaml`. Новый продукт подключается новой карточкой, без правки кода и промпта.

## Защиты — в инструментах, а не в промпте

Даже если модель ошибётся или поддастся инструкции, спрятанной в тексте обращения, инструменты не дадут:

- создать задачу по кластеру ниже порога частоты;
- сослаться на тикеты не из этого кластера (защита от выдуманных доказательств);
- записать персональные данные в задачу, комментарий или дайджест;
- превысить лимит записей за прогон (15 на продукт);
- создать дубль (идемпотентность по `cluster_id`) или прокомментировать закрытую задачу;
- отправить дайджест дважды.

Каждая защита покрыта тестом в `tests/test_tools.py`.

## Оценка качества: что проверяет офлайн-режим, а что нет

`MockChat` подменяет только языковую модель. Извлечение карточек в нём работает по ключевым словам, решения агента принимает детерминированная политика, которая буквально следует разделам 3–4 промпта. Оркестратор, формат сообщений, инструменты, защиты, хранилище и доставка — те же, что в бою.

Поэтому `eval` в офлайне показывает 1.0 по всем метрикам. Это проверка того, что вся цепочка собрана правильно, а не оценка качества Qwen. Качество модели меряется тем же `eval --online` на золотом датасете из 1 000 размеченных обращений из архива. Пороги приёмки зашиты в `signal_agent/__main__.py`: precision ≥ 0,75, recall ≥ 0,85, macro-F1 ≥ 0,80, purity ≥ 0,80.

## Данные

`data/generate_sample.py` детерминированно генерирует 66 обращений. Темы взяты из примеров кейса, плюс шум, инцидент и вымышленные ПДн для проверки маскирования. Рядом лежат золотая разметка (`golden.jsonl`), ожидаемые решения (`expected_decisions.json`), стартовый бэклог (`backlog_seed.json`) и прошлые оценки команды (`feedback_seed.json`).

## Что меняется при переходе в бой

- SQLite → PostgreSQL + pgvector: схема в `storage.py` переносится один в один, сырые тикеты выносятся в отдельную схему без доступа сервиса агента.
- TF-IDF → эмбеддинги внутренней модели через `Embedder`.
- `SqliteTracker` → адаптер к корпоративному трекеру, `FileDigestSink` → вебхук мессенджера.
- Регулярные выражения ПДн дополняются NER-моделью во внутреннем контуре.
